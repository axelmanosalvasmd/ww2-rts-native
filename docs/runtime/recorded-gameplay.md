# Recorded gameplay input

The internal `Command` enum and `OrderQueue<Command>` carry supported gameplay inputs. The host assigns `OrderKey { tick, issuer, sequence }`; ascending keys determine dispatch regardless of arrival order. `apply_commands(T)` requires the Match clock at T-1 and runs before the runner increments it. This keeps source command timestamps, spawn ghosts and route keys at the input boundary. Automatic simulation effects and reconnect/disconnect lifecycle changes keep their existing phases.

Move, attack-move, Stop, stance, Ability, Autocast, Support, Buy, Tech and ordinary Dig share that queue. Each dispatcher branch delegates to its canonical component transaction. Unit waiting orders contain only represented per-unit intent; purchases, research, support and companion bindings never enter those waiting orders. Unsupported gameplay kinds remain explicit. This adds no socket endpoint, wire field, C call or server match admission.

`Command::from_json` preserves whole malformed-order rejection before choosing an ordinary command type. Buy reads the source `unit` and optional `from`; an omitted maker stays absent, while a present invalid maker becomes the impossible ID zero. Production still checks faction, technology, resources, population and limits before maker selection. Tech accepts the source names `tier`, `inf`, `guns` and `armor`. Purchase and research denials retain their component's source reason. Internal state errors propagate to the Match runner rather than becoming ordinary gameplay refusals.

A successful purchase prepares placement, owner-bound rally routing, source MP-spending story, identity admission and metadata before payment. Publication installs control, combat, firing, ability and recovery rows without a later fallible step. Canonical wallet and lab guards perform research admission and story publication. Support and abilities retain their component admission and effects; their pending source-only prerequisites do not establish complete tick execution.

Trusted companion Join and Input carry `CompanionJournalId`, a nonzero match-scoped integer assigned by the authenticated host. Its fixed registry key is `journal-companion:{id}`. Raw gameplay JSON cannot construct either variant, and the core records no credential text. The key resolves through the existing companion registry, whose dispatch-allocated CompanionId remains separate. An existing owner's identity cannot be reassigned through another issuer. The host preserves that original owner when binding reconnects. No second identity registry is introduced.

FPS input runs through its source-specific gates before ordinary commander-away admission. Join checks owner existence, elimination and winner; Input retains online, sequence, finite movement, bounds and edge-count checks. Repeated, stale, invalid and foreign-owner inputs leave state unchanged and produce no gameplay denial. Room role, commander-count and non-World admission remain host responsibilities. Automatic respawn remains a lifecycle phase, with the complete staged batch checked before wallets or publication change. Every fresh companion reserves ability/recovery identities and publishes their source defaults beside combat/firing.

Its distant approach uses the same path-request scheduler, with descriptor-derived eligibility and goals. Accepted Move and Stop synchronously cancel that descriptor; a failed Dig route cancels it at the existing retry limit. The checked path API restores its request owner before propagating a cancellation error. Queued digs, construction, bridge, wall, gate and fill work remain explicitly unsupported. Twelve original-source traces with 47 actions regenerate exactly; native replay and unit-loop integration remain pending.
