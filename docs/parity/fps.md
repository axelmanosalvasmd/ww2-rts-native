# FPS companion (FPS)

Pin: `reference/ww2-rts` at e4e579a. Every path is relative to `reference/ww2-rts`. The `fps` message, the operative `start` and the `operative` status block are specified in [`protocol-messages.md`](protocol-messages.md).

An operative (companion) is a teammate who plays one rifleman of a human commander's army in first person. The commander keeps the army; the operative takes no army seat. The simulation side lives in `shared/sim.js` (`joinOperative`, `operativeInput`, `stepOperative`, `fireOperative`, `throwOperative`, `spawnOperative`, the squad lead), the room side in `server.js`, the browser side in `client/operative-view.js` and `client/operative-controls.js`.

Test key: `test-operative.mjs`, `test-operative-client.mjs` and `test-operative-server.mjs` have no named checks; they are cited by `file:line` and the assertion message. `tools/test-operative-browser.mjs` (real Chromium under X11) and `tools/test-operative-public.mjs <https URL>` are manual acceptance scripts outside `node test.js`.

## Native bounded runtime

`companions.rs` and `match_companions.rs` implement internal Match entry, input validation and press baselines, movement/collision, loadout timers, ordinary-command squad following, death hooks and staged respawn batches. Positions, health, control intent and weapon timers retain their canonical owners. [Runtime scope](../runtime/fps.md) records the source oracle and integration boundaries. All marked rows remain in progress until the full room, combat, snapshot and client paths are wired and accepted.

The separate [effects follow-up](../runtime/fps-effects.md) implements drawn squad bodies, sampled visibility-filtered rays, staged Combat-stream randomness, canonical damage/shot publication and shared typed grenade launches. Seven effects tests pass in debug and release against 49 source traces, 39 geometry cases and 66 operations, including 11 launches/77 samples under both ordinary mode aliases. The combined check also passes 174 locked release workspace tests and independent debug/release replay. These component checks do not establish tick dispatch, grenade settlement, transport or client acceptance.

Admission and message capability helpers do not install a new server role or its 20 ms transport throttle. The companion step returns fire/grenade requests; their canonical effect methods now resolve damage, events, ammo and counters when called. Scheduling those methods remains integration work. Generic retirement requires companion preflight and bookkeeping hooks from the tick caller; this phase does not remove ordinary units itself. The pending hit-direction privacy proposal is unchanged.

## Existing limitations

- **World Conquest is refused** for companions (server.js:606, 309; FPS-MVP.md:59). If the host switches the room to World after operatives joined, they get no `start` at all (server.js:309).
- **Four companions per room life.** `room.operatives` is never shrunk (server.js:607 is the only write besides the initial `??=`), so after four different tokens join, no new companion can join that room even if the first four left.
- **Orphaned companions.** The operative is bound to the commander's player object (server.js:607). If that seat is freed (lobby cleanup, match end) the lobby shows "departed commander" (`commander: -1`, server.js:342; client/main.js:370) and no later start reaches the operative (server.js:308-309). Nothing re-attaches it.
- **A refused operative reconnects forever.** After `deny join` and close 1008 the browser connection retries with backoff (client/connection.js:23, 51-54); the deny text falls back to "That order cannot happen" because `commander` has no sentence (client/availability.js:6-22).
- **Commander can scuttle the operative's soldier.** `destroy` filters only by owner, HP and riding (shared/sim.js:3763), so a commander's scuttle kills the companion's soldier; respawn then costs 10 MP. No test covers it.
- **Hidden shooter position in the status.** `operative.from` carries the attacker's launch point to 1 m for 10 ticks after any hit (server.js:305; shared/sim.js:2091, 4211, 4222), even when that unit is under fog. The client uses only its angle (client/operative-view.js:342), but the coordinates reach the companion's socket.
- **No backpressure for operative sockets** (server.js:320-328; compare server.js:762-776 for seats).
- **Rapid input changes are dropped.** The client sends on every input event (client/operative-view.js:128) but the server keeps one message per 20 ms (server.js:633). Counted presses survive; a short `fire` or key state can lag until the next 50 ms heartbeat.
- **Allies do not see the operative flag.** The non-owner mask clears bit 17 (shared/sim.js:5903), so other seats, including teammates, draw the companion as a one-man rifle block at a block slot rather than "on his own spot" (client/main.js:948-950).
- **Coarse bodies remain** for squads in trenches and houses, vehicles and structures; no per-limb hitboxes; the per-man body ignores kneeling and prone poses (shared/sim.js:2060; CHANGELOG.md:294-295).
- **The man a squad gives up for a respawning operative drops as a corpse on clients** (CHANGELOG.md:294).
- **Operative fire does not damage terrain or buildings.** `hurt` is applied to units only (shared/sim.js:2090); FPS-MVP.md:59 lists building damage as absent.
- **Unseeded spread.** `fireOperative` uses `Math.random` (shared/sim.js:2055), so hits are not reproducible from inputs alone.
- **Desktop only:** pointer lock, keyboard and mouse, HTTPS or localhost (FPS-MVP.md:59; client/operative-view.js:81).
- **Prototype presentation.** FPS-MVP.md:59: art, performance tuning, audio, input reconciliation and balance are prototype-grade.
