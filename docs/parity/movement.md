## Determinism notes for the issue #2 port

Step order
- Units step in `g.units` insertion order with live iteration (MOV-02). Separation runs over the `list` snapshot taken after the loop (sim.js:5605), in that order, with a fresh 4 m grid built from `g.units` (sim.js:5190).
- Deferred route requests run in FIFO order at the start of the tick, before any unit, and add one TICK to the served unit's `repath` (sim.js:5337, 3230-3247).
- `g.strikes` resolve in call order; Fighter Cover zones are matched with `find` (first in array order); flak rolls go through `list` order (sim.js:5244, 4697, 4700).
- Operatives spawn before the loop and step inside it (FPS).

`Math` functions used by movement, grid, routing and support (checked V8 13.6.233, the V8 in Node 24.21.0 on this Mac)
- `Math.hypot` (2 and 3 arguments): V8 13.6.233 computes sqrt((a/m)² + (b/m)²) x m for two arguments and a compensated sum for three (src/builtins/math.tq `FastMathHypot`, fetched from the 13.6.233 tag); TurboFan does not inline it. Rust's `f64::hypot` differs in the last bit; port V8's formula. Sites: `dist` (sim.js:561) and every distance check, walkable (sim.js:2860), postCost (3119), endSpots (4031), separation (5207), airBase (2188), movement.js:8, 48; vehicle-motion.js:18, 48, 98, 106, 132, 168, 178; local-traffic.js:10, 88, 113, 115, 119, 148; grid.js:111, 116; navigation.js:246, 296; debris-motion.js:14, 51 (3 args), 48; world-rails.js:23, 79-80.
- `Math.atan2`, `Math.sin`, `Math.cos`: movement.js:17, 22, 24, 32-33, 66, 68; vehicle-motion.js:19-20, 28, 94, 97, 99, 105, 109, 118; sim.js:557 (strike strips), 1072, 1091-1095 (stepOut rings), 1774-1775 (spawn angle n x 2.4), 1281 (train), 1294 (train unload ring), 2222-2224 (plane orbit and heading), 3687 (support direction), 4075, 4078-4079, 4107-4108, 4148, 4859-4860 (smoke drift), 5261 (paradrop ring), 5537, 5554, 5625; debris-motion.js:10; world-rails.js:30, 33. Node's v24.x gyp files do not define `V8_USE_LIBM_TRIG_FUNCTIONS`, so sin and cos are probably V8's fdlibm port; confirm on the server's node binary. Rust should use an fdlibm-faithful port and a differential test against Node.
- `Math.tan`: movement.js:67. `Math.exp`: debris-motion.js:46-47.
- `x ** 2`: vehicle-motion.js:90. V8 returns x * x for exponent 2 on both pow paths (src/numbers/ieee754.cc and base/ieee754.cc `legacy::pow`, 13.6.233), so `x * x` in Rust matches. `end` can be Infinity there (turnSpeed returns Infinity under 1e-3 rad); IEEE behaviour is the same in Rust.
- `Math.sqrt` (vehicle-motion.js:90, sim.js:4031, 4148, 5625): correctly rounded, safe.
- `Math.round` (local-traffic.js:7 ghost ticks, sim.js:3556 rail cooldown, sim.js:4026 group keys, world-rails.js:33, 92): JS rounds halves toward +infinity, Rust's `f64::round` rounds away from zero; use floor(x + 0.5) semantics.
- `TICK` is the double nearest 0.05; keep every dt product in the same order of operations.

Randomness
- Movement, traffic, grid, routing and vehicle code draw no random numbers.
- Unseeded global `Math.random` in MOV scope: artillery shell spot, 2 draws each (sim.js:5287); bombing sideways jitter, 1 per bomb (5280); smoke cloud jitter, 1 per cloud (5273); flak roll per eligible gun until one hits (4705); shot-down remainder for bombing and recon only (4710); bomber area sticks, 2 per bomb via `launchSalvo` (4148); salvo landing, 2 per shell at sim.js:5625, drawn even for physical salvos whose result is thrown away. These interleave with combat (`fire`, sim.js:4171-4172), operative (2055) and AI draws in one process-wide stream.
- `g.seed` itself comes from `Math.random` at match creation (sim.js:772) and feeds `rng(g)` for wind, which moves smoke (sim.js:4859-4860).
- Parity runs replace `Math.random` with a mulberry32 stream (tools/bench-move.mjs:23-30; test.js:460 pins it to 0.5). The Rust core must consume the same stream in the same order, dead draws included.

Map, Set and order-dependent iteration
- Grid `unordered` and `heavy` return raw bucket order: cells z then x, and inside a bucket the order after the last rebuild with units moved this tick appended at the end. Order-dependent consumers: movement.js:44-45 (`nearby.find`: the first blocking unit decides whether an ally ghost starts), local-traffic.js:80-92 (`oncoming.find`: which friend holds the lane, stored in `queuedBehind`), sim.js:3992-3993 (`threatFor` ties), sim.js:5141-5143 (debris contact ties). The comment at local-traffic.js:94 ("nearby is unordered...") holds only for `trafficStep`'s conflict loop. The Rust grid must reproduce bucket order exactly, not only membership.
- `inOrder` is Map order: separation pairs, `antiAir` (`<=`, so the later of equal-distance planes wins, sim.js:2244), target choice.
- `navigation.js` region `edges` are Maps whose insertion order sets neighbour order in `routeFor` (equal costs keep the first `came`); `updateChunks` deletes and re-adds edges and reuses freed region ids last-in first-out (navigation.js:170-175, 190); the heap breaks ties by region id. Coarse routes therefore depend on the cache's update history, not only on current terrain.
- WeakMap caches keyed by game or view objects (grid index, region labels, coarse graphs, vehicle views, wall-adjacency, observed path views, path queue, retry counts) are not iterated, but the coarse graph, the path FIFO, retry counts and `laneScan` carry state. A save and reload drops them, so a restored match can route differently from an uninterrupted one.
- Region label values (`relabelNear`) are compared only for equality; their numbering does not matter.

Typed-array rounding
- A* g-scores live in a Float32Array (sim.js:2868) while costs are computed in doubles; the heap stores the unrounded double `cost + h` (sim.js:2870, 3161), `gs[n]` stores float32(cost), the next expansion adds to the float32 value, and `cost < gs[n]` compares a double with a widened float32.
- Vehicle step costs and bunker penalties are cached as doubles (Float64Array, sim.js:3132-3133).
- `g.wear` and `g.surfaceWear` are Float32Array (sim.js:765-766): traffic wear accumulates in float32 (sim.js:5522) and live speed reads it, while remembered views quantize wear to quarters (sim.js:1527, 1640), so route costs and actual speed see different wear.
- world-rails.js:10 cost grid is Float32Array; the laid-track discount stores float32(0.6) (world-rails.js:88).
- Heights are Int8Array and flags Uint16Array: exact.

Found while porting (2026-10-12)
- `sim.js` defines its own `ghostPair(g, a, b)` (sim.js:1099: allied, and either a ghost) over the `ghostPair` it imports from local-traffic.js as `ghosts`. Separation's solid contact (sim.js:5212) uses sim.js's, so a ghost softens a push between allied vehicles.
- `laneScan.path` and `motionClearance.path` are compared with `u.path` by identity (local-traffic.js:70, movement.js:18). The core gives each unit a route generation number instead; a saved and reloaded game loses identity, so its scans and clearances count as made on another route.
- `suppMul(u)` is taken at the top of the unit's turn (sim.js:5345), before suppression wears off that tick (sim.js:5362).
- `weather()` (sim.js:4858-4870) runs every tick even when `stepWeather` does not: it drifts smoke, and in Clear weather toggles showers after `wx.next` seconds and dries or soaks the ground, which the movement speeds and the dust flag read.

Wall clock and scheduling
- No movement code reads the clock; dt is the fixed TICK. The path budget counts searches, not time (sim.js:3233).
- The server polls every 10 ms, runs up to 4 due ticks and drops a larger backlog (server.js:791-799): this changes how many ticks run per second, not their results. Command arrival between ticks is NET's concern; AI seats think after `step` (server/room-tick.js:12-22).
- `pathBuffers` is module-level scratch shared by every game in a process (sim.js:2864-2873); safe because searches are synchronous. Generation counters wrap at 2^32 with a full clear.
