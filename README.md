# Three Crossroads Native

The native rebuild of Three Crossroads, the WW2 RTS in [ww2-rts](https://github.com/axelmanosalvasmd/ww2-rts): an Unreal Engine 5.8 game client and a Rust server, sharing one Rust rules core.

**Status: step 1.** The Rust core has its math, spatial grid, vision, fog, movement and crowd separation ported and checked against the JavaScript, and the first C calls for Unreal; Axel's Unreal client runs against the Node server. An internal Rust recipient view is checked against recorded browser state; its six jointly approved ABI 2 C calls became authoritative through PR #16, merged at `d88ef6d`. The approved header is unchanged.

Axel's consumer source is published in draft [PR #201](https://github.com/axelmanosalvasmd/ww2-rts-native/pull/201) at `9551d3976e9145c81030cf5a81ec7f0764b04d12`, explicitly not for merge, and is not adopted on main. Axel reports Linux build and automation checks against Rust `92fb7fe`; the earlier live and packaged-client evidence uses `03a49ac` and was not rerun on that newer library. The draft uses Rust unit rows by default but retains the C++ fallback, row tails, cells, fog and independent row parsing. Fresh live adoption, Windows/macOS client and input checks, physical mouse/keyboard tests and broader rules-query integration remain pending.

The Rust server hosts lobbies and reconnectable sessions. A trusted host can attach a supported Default or Conquest match; seated players can send Move, attack-move, Stop and Stance through the existing recorded queue. Public network start/restart, other command families and unsupported contexts remain guarded. PR #198 merged this bounded input path and the internal table/terrain providers at `514e15f4`, after exact-head native and three-platform verification and Axel's no-objection review. Table transport #199 and Unreal adoption remain separate. Step 1 is two measuring tests that decide whether the plan goes ahead:

- #1: the plan, the measured limits and the decision.
- #2: sim test, the hot path in Rust against Node at 400, 1,000 and 2,000 units.
- #3: Unreal test, a real map and 2,000 soldiers drawn from today's server, with the Rust core linked on Windows and Mac.

Diagrams of the whole plan: https://claude.ai/artifact/WVbpVy8k7zF7oQrYYp1UER

## Why

In ww2-rts, one battle's tick runs on one server thread. A heavy battle of about 400 units already uses 34 of its 50 ms at p95. The browser client draws, builds terrain and runs game logic on one main thread too. The goal is thousands of units per battle and, later, a public release. Details and sources are in #1 and `DESIGN.md`.

## How it fits together

| Part | Runs on | Language | Job |
| --- | --- | --- | --- |
| Rules core | both | Rust | The game rules: same seed, same match. No engine code. |
| `ww2-server` | the host | Rust | Runs battles, one thread per room, a battle's tick split across cores. |
| Game client | each player's PC | Unreal 5.8, C++ | Draws the world, HUD, effects and sound. Never decides outcomes. |

The client links the rules core through a small C interface for placement checks, prices and moving your own units between updates. Everything else crosses the network.

## Layout

```

rust/                Cargo workspace, pinned to Rust 1.99.0
  crates/core/       rules core: no engine, networking or file-system code
  crates/simtest/    loads harness states into the core and checks it against the JavaScript
  crates/server/     HTTP/WebSocket lobby, sessions and bounded trusted native matches

  Plugins/WW2Core/   the Rust core's C interface (ww2-ffi) and its Unreal wrapper; the library is build output
  Tools/             scripts that make the generated content, tables and packages, and run local servers
DESIGN.md            decisions and measurements
PARITY.md            what the JavaScript prototype does, and how the native game is measured against it
docs/parity/         the inventory by area (modes, maps, combat, server, ...)
AGENTS.md            rules for agents working here
CHANGELOG.md         every change, in plain words
```

## Getting started

```
git clone --recurse-submodules https://github.com/axelmanosalvasmd/ww2-rts-native.git
# or, in an existing clone:
git submodule update --init
git lfs install --local
```

You need Rust (stable) for `rust/`, Node.js to run the reference game and its tests, Git LFS, and Unreal Engine 5.8 only for `unreal/`.

## Unreal client (slices 1a to 1ac)

Slice 1ac fixes disabled training-slot observation between HUD draws, the clipped history-bottom row, original secondary Build symbols and apron texture anisotropy. The required-FFI editor passes 220 unique Intel Vulkan tests (214 clean and six warning successes). Linux Development slice28 builds and runs bounded High/Low, session and saved-settings controls. Renderer, R1 and acceptance limits remain explicit in [the design note](design.d/2026-10-20-unreal-slice1ac.md).

Built and run on Linux with the installed Unreal 5.8.3; Windows and Mac are not built yet. The project uses the engine's empty Entry map and spawns everything from C++.

The repository holds the client's source, config, the WW2Core plugin's source, the tools and two small generated text tables (`unreal/Content/Data/units.json` and `locale-es.json`). Every binary asset the client loads is generated from the pinned reference by a committed script and is not committed (`.gitignore` lists the folders). Without them the editor target still builds and 52 of the 56 automation tests pass (the other 4 load that content); the client logs what it cannot load and leaves it out. Make them in this order (each tool's README has the details and its checks):

| Folder | What | Made by |
| --- | --- | --- |

| `Content/Models` | 261 unit, building, piece and plant models with their materials and textures | `unreal/Tools/models` (export under Node, then `import-models.py`; see its README) |
| `Content/Models/Infantry` | the soldier rig, kit and crowd figures | `unreal/Tools/models/infantry/run.sh --unreal` |

```
UE=~/Applications/UnrealEngine-5.8.3   # the engine folder

# build the editor target (the module the game runs in)
$UE/Engine/Build/BatchFiles/Linux/Build.sh ThreeCrossroadsEditor Linux Development -project="$PWD/unreal/ThreeCrossroads.uproject" -waitmutex

# an isolated reference server: a copy of reference/ww2-rts at its checked-out commit, on a free 127.0.0.1 port
unreal/Tools/tc-local.sh serve
unreal/Tools/tc-local.sh health   # process, HTTP 200 and a WebSocket hello answered by a lobby

# play: opens a window, hosts room native1 with one AI and starts (TC_ROOM, TC_NAME, TC_AI change that)
unreal/Tools/tc-local.sh play
unreal/Tools/tc-local.sh host     # the same window left in the lobby: Mode, Add AI and Start match are HUD buttons
unreal/Tools/tc-local.sh join     # a second player on this machine (its own seat label)
unreal/Tools/tc-local.sh watch    # a spectator
unreal/Tools/tc-local.sh check    # no window: a headless client starts a match in its own room and moves
unreal/Tools/tc-local.sh stop     # stops only the server this script started
```

The server copy, its pid, port, saves and the logs live in `unreal/Saved/LocalServer/` (ignored by git; `TC_RUN_DIR` moves it). The script never touches another server.

Client options: `-TCServer=ws://host:port/ws`, `-TCRoom` (3 to 12 letters or digits), `-TCName`, `-TCSpectate`, and where the seat token comes from:

- `-TCSeat=<label>`: one token per server, room and label, kept owner-only in `unreal/Saved/TCTokens/` and locked while the client runs, so two clients on one machine need two labels (a second client on the same label is refused).
- `-TCTokenFile=<absolute path>` or the `TC_TOKEN` environment variable, for a token kept elsewhere.
- `-TCSpectate` always uses a throwaway token, so a watcher can never take a seat.

The token is the seat's key, so it never goes on the command line: `-TCToken=` is refused, because the engine writes its command line into the log and `ps` shows it to every local user. An old `unreal/Saved/TCToken.txt` is no longer read; delete it.

Controls: F1 opens the Controls sheet with every key (F1 or Esc closes it). WASD, arrows or screen edges pan (the edges once the pointer has moved in the window, as in the browser; the zone ramps over 24 to 48 px and eases in, and Edge scroll and Pan speed in the Orders panel switch it and set the speed, saved), the wheel zooms at the point under the cursor (out to the whole map), Q/E or a middle drag rotate, and a new match glides in from the whole map to your spawn (any key or click skips it). Left click or drag selects your units (a drag leaves supply trucks and trains out). Right click orders them as the browser does: on an enemy unit it attacks, on the ground it moves, and Ctrl+right click attack-moves. X stops the selection. G arms an attack-move for the next left click (right click or Esc disarms it). Shift queues an order. Esc clears the selection. Keys match the browser's chords exactly, so Shift+X and Shift+G are stances, not Stop and Attack-move. Digits 1 to 9 are control groups: Ctrl+N sets group N, N recalls it (twice quickly centres the camera on it), Shift+N adds the selection, Alt+N moves the selection's army into N and out of every other group. The minimap (bottom right) turns with the camera: a left press or drag points the camera there, a right press orders the selection there (Ctrl attack-moves, Shift queues). The HUD shows the lobby (seats, mode, map and, for the host, Mode, Add AI and Start match buttons), the selection (one unit's health and target, or counts by type), the enemy under the pointer, the control groups, Stop, Attack-move and (host) End match buttons, the recruit card, what the last order did, and a refusal in the browser's words. The recruit card is the browser's Command Card: outside Classic, group tabs and every unit your side can recruit, with its price, army use against the limit, and why a card is unavailable (hover it); a click buys one, Shift+click up to five. In Classic and World, select a Production Building to get its units, its training line and five queue places; a click on a waiting place cancels it for a refund.

Construction, logistics and army commands (slice 1d), as the browser does them: the Orders buttons (Stop, Attack-move, Retreat, Hold fire, Hold position, Auto-retreat with each one's Off, On or n/N state) show for a selection that is not all buildings or all trucks. With a builder squad selected (rifle, conscript or engineer squads outside Classic) the Orders panel has a Build menu of base buildings; in Classic and World an Engineer selected turns the card into the Build card, and J, K, L, O and Y arm the Supply Depot, Barracks, Motor Pool, Airfield and Flak Emplacement. An armed building shows its footprint under the pointer, green where the browser's placement check passes and red where it refuses with the reason; a left click builds there (Shift keeps it armed), a right click or Esc cancels. R retreats the selection; Shift+F, Shift+G and Shift+X switch hold fire, hold position and auto-retreat; Shift+H (or the recruit card's Rally button) arms a rally: the next left click, in the view or on the minimap, sets the army's rally point, or the selected Production Buildings' rally (in Classic and World a Production Building must be selected). A right click with Production Buildings selected sets their rally too. With only trucks selected, a right click on a friendly unit or Supply Cache sends them with supplies (an ally's cache: the supplies are held for that ally), and Resume deliveries puts them back on automatic runs. The logistics card lists each selected unit's ammunition, provisions and fuel, a truck's cargo and route, and a friendly store's stock as this seat may draw it; Supply overlay draws known stores and the selected trucks' fully known routes (also on the minimap), and Truck select makes a drag take only your trucks. Supply alerts show under the status lines. Rail is not built yet (cover, area fire, support powers and formations came in slice 1f).

Formations, support calls, area fire and the cover preview (slice 1f), as the browser does them. Lobby settings, saved matches and the map's objects (slice 1g), as the browser does them. The lobby shows each setting as a button: a left click picks the next choice, a right click the previous. The host sets the Map (World size in World Conquest), the Mode, the Army size, the Assault defender, each seat's Team and each AI's difficulty and faction; every player picks their own Faction. A setting this client may not change is greyed and its reason shows under the pointer; a change stays marked "asked" until the server's next lobby shows it (the server ignores a change it refuses). Start shows the browser's text and is refused, with the browser's reason, when the seats do not fit. Objectives, the end of the match, order feedback and the keys (slice 1i). A score strip at the top centre shows each mode's score as the browser does: in Conquest each team's victory points against the goal with a bar, each player's points and points held, online state and ping; the lead block in the other modes (Assault clock and structures, Annihilation bunkers, Classic Sudden Death, Horde wave, Tutorial step, World regions). F2 (stats) and Tab (recruit mode) say they are not in this client yet.

Combat effects, alerts, map pings, sound and Spanish (slice 1j). Shots, projectile flights, fires, smoke screens and falling sections are drawn from what this side's snapshots carry, as the browser's `fx.js`, `projectiles.js` and `debris.js` choose them: muzzle flashes and tracers only at a shooter this side holds, impacts only for delivered shots, explosions, smoke, dust, scorch marks and a small screen shake, all as coloured engine shapes (placeholders, not the browser's sprites). The alert feed now also has the browser's unit alerts (under attack, base under attack, unit lost, enemy air incoming, unit ready, building finished, scripted lines). Alt+left click on the ground or the minimap pings that spot to your team: each teammate gets a ring there for 4 s, on the minimap too, a click and a "Ping from <name>" alert. Sound follows the browser's mixer: weapon, impact and explosion sounds placed from the camera, your faction's voice for move, attack, retreat and lost, alert and UI sounds, the match start, the tank engine and ambience beds; M mutes and the Volume button (with the Orders, every match) steps the volume by 10 points, left up and right down, saved. The Language button (with the Orders, and in the lobby) switches between English and Spanish at once and is saved; every HUD text is shown through the reference's Spanish dictionary and rules, so what the dictionary does not have stays English, as in the browser.

Unit models. Units are drawn with the reference game's own models, converted from its builders (`unreal/Tools/models`, see its README for the whole chain): tanks, guns, vehicles, aircraft, boats and base buildings with their faction paint and your player color on their markings and on the ring under them, turrets turned toward what they aim at, buildings rising while they are built, and soldiers in the reference's poses (standing, crouched, prone, running, digging) that walk in their squad's formation as the browser's do. Beyond 110 m from the camera soldiers and crew guns switch to the reference's far-away figures. A type without a model would fall back to the old placeholder shape; `-TCModels=none` brings the placeholders back for a run (or `-TCModels=pilot,vehicles,infantry,airnaval,structures`, any of them). Carrier riders use the original far kneeling figures, three per carried squad, with source hull-derived deck seats.

### Rust core bridge (ww2-ffi, Linux x86_64 only)

The `WW2Core` plugin links the Rust core's C interface (`libww2_ffi.a`, ABI 2: version, rules hash, slot size and formation spots, plus the six `ww2_view_*` recipient-view calls) when it is installed. Every formation move (the plain click, a facing drag, a re-form, any shape and spacing) then takes its spots from the core, and the recipient view supplies the unit rows (`TC_DECODER`, slice 1l). Without it the client builds and runs as before on its interim C++ port, and says so in the build output and the log. The library is never committed: build and install it from a pinned native commit with

```
# a clean clone of ww2-rts-native at the pinned commit (made under unreal/Saved/WW2Ffi, or WW2_NATIVE_SRC=<clean clone>),
# built with the toolchain that commit pins (rustup installs it user-local: the script prints the command if missing)
unreal/Tools/ww2-ffi.sh build     # or verify: also the crate's own tests and its C example against the fixture
unreal/Tools/ww2-ffi.sh status    # what is installed and whether it still matches its STAMP
# then build the editor target as above; set TC_REQUIRE_WW2_FFI=1 to make a missing library a build error
$UE/Engine/Binaries/Linux/UnrealEditor-Cmd "$PWD/unreal/ThreeCrossroads.uproject" -nullrhi -ExecCmds="Automation RunTests ThreeCrossroads.WW2Core+ThreeCrossroads.Formation; Quit" -TestExit="Automation Test Queue Empty"
```

The pin is `WW2_FFI_REV` in the script (native `main` at `92fb7fe`, which carries PR #16's ABI 2 unchanged). A partial install, or a file that no longer matches its STAMP, stops the build. Windows and Mac are pending: the plugin builds there without the library. Formation spots and the unit rows go through the core; the rest is still the client's own interim code, including the C++ decoder, which stays as the fallback (see `DESIGN.md`).

### Linux package (Development, Linux x86_64)

A packaged client: RunUAT BuildCookRun of the game target (not the editor module) with the installed Unreal 5.8.3, cooked to a pak and IoStore containers, with the Rust core linked into the one executable. It is the first packaged milestone, not a release, and it has no server inside: it needs the **temporary** reference backend, the pinned JavaScript server on Node (`tc-local.sh serve`), until the Rust ww2-server exists. The package does not contain Node or that server.

```
unreal/Tools/ww2-ffi.sh build                 # once: a package always links the Rust core (no interim fallback)
unreal/Tools/tc-package-linux.sh check        # engine, Linux game target, toolchain, .NET, disk, ww2-ffi STAMP, generated tables
TC_PACKAGE_OUT=<output folder> unreal/Tools/tc-package-linux.sh build
unreal/Tools/tc-package-linux.sh verify <package folder>   # the static checks again

unreal/Tools/tc-local.sh serve                # the temporary reference server; tc-local.sh status prints its URL
<package>/tc-client.sh --server ws://127.0.0.1:PORT/ws --room native1 --seat host -- -windowed -ResX=1600 -ResY=900
<package>/tc-client.sh --server ws://127.0.0.1:PORT/ws --check   # check the machine and the server, start nothing
```

`build` copies the project's sources, config, content and the installed ww2-ffi to a work folder (`TC_PACKAGE_WORK`, default `unreal/Saved/PackageWork`), so the editor build in `unreal/Binaries` and `unreal/Intermediate` is never touched; runs BuildCookRun there with `TC_REQUIRE_WW2_FFI=1` and at most `TC_PACKAGE_JOBS` compile processes (default half the cores, at most 8); checks the result (an x86-64 executable whose shared libraries all resolve, no editor module, the `ww2_*` entry points and the STAMP's native commit compiled in, `Content/Data/units.json` in the pak, the Entry map, the engine shapes, materials and font the client loads by path, and the shader archives in the cook); and only then replaces `TC_PACKAGE_OUT` (default `unreal/Saved/Packages/ww2-rts-native-linux`). The package holds `Linux/` (Unreal's staged game), `tc-client.sh`, `README.txt`, `BUILD-INFO.txt` (engine, toolchain, native commit and a digest of the packaged sources, reference commit, the ww2-ffi STAMP, the exact UAT command), `SHA256SUMS` and Unreal's staging manifests. `TC_PACKAGE_CLEAN=1` builds from nothing, `TC_PACKAGE_DEBUGINFO=1` keeps the separate debug files.

`tc-client.sh` stops with a plain message when the architecture, a shared library, a Vulkan driver, a display (pass `-- -RenderOffscreen` or `-- -nullrhi` without one), the server URL or an answering server is missing, and refuses `-TCToken=`. It passes `-TCServer`, `-TCRoom`, `-TCName` and `-TCSeat` (or `-TCSpectate`), and keeps settings, seat tokens, logs and screenshots in `-UserDir` (`~/.local/share/three-crossroads-native`, or `--user-dir`/`TC_USER_DIR`), never in the package. Anything after `--` goes to the client, including the unattended `-TC` switches above.

`unreal/Content/Data/units.json` comes from `node unreal/Tools/export-unit-table.mjs`, which reads the pinned reference. The recruit table in `Client/TCRecruitment.cpp` comes from `node unreal/Tools/export-recruit-table.mjs reference/ww2-rts` the same way, the construction table `Client/TCConstructionData.inl` from `node unreal/Tools/export-build-table.mjs`, and the ability table and its test cases (`Client/TCAbilitiesData.inl`, `Client/TCAbilitiesCases.inl`) from `node unreal/Tools/export-ability-table.mjs reference/ww2-rts` (`--check` compares without writing). Recruiting, building, abilities and field works are refused unless they name the same reference commit as `units.json`. ## Relation to ww2-rts

- ww2-rts stays the playable game until the native game replaces it, and gameplay changes keep landing there.
- `reference/ww2-rts` pins the ww2-rts commit the native game is measured against. That game is a prototype: `PARITY.md` lists what it does and how the native game carries it over, improves it or drops it. Moving the pin is its own commit, together with the port of whatever rules changed.
