# Three Crossroads Native: design decisions

The plan, its evidence and its open work are issue #1. This file records what was decided and why, and the measurements as they come in. Paths such as `shared/sim.js` refer to the JavaScript game in `reference/ww2-rts`.

## Why native (2026-10-11)

Measured in ww2-rts:

- **Server:** one battle's tick runs on one thread. A heavy Conquest battle (Six Fronts, six Massive AI, about 400 units) costs 16.3 ms mean and 34.0 ms p95 of the 50 ms tick in Node (`tools/bench.mjs`, ww2-rts#58). Bun is 1 to 14% faster. `WW2_SHARDS=N` (`server/shards.js`) spreads separate rooms over processes, but nothing splits one battle.
- **Client:** the browser's main thread draws, builds terrain and runs game logic. A three-human Huge World Conquest session fell to 0.7 FPS; after the ww2-rts#61 fixes it runs at about 30 FPS on an RTX 4060 with 12.6 ms of frame-loop JavaScript.
- **Crowds:** 2,160 soldiers near the camera run at about 35 FPS on Low and 21 to 23 on High in the ww2-rts#64 synthetic fixture; the GPU spends 22 to 41 ms a frame on that scene.

The goal is thousands of units per battle and a public release later. ww2-rts#64 concluded its own measurements don't justify a rewrite, so step 1 measures before anything is ported.

## Architecture (2026-10-11, pending step 1)

Two programs talking over the network, as today. Only the rules core decides outcomes.

1. **Rules core (Rust, `rust/crates/core`).** Port of `shared/`. 20 ticks a second. The same seed gives the same match. Unit, weapon and map tables live in data files both sides read. No engine, networking or file-system code.
2. **Room host (`ww2-server`, Rust).** One thread per room; a battle's tick is split across cores and merged in a fixed order. AI planning and long path searches run on worker threads and apply at a fixed future tick, so the battle never waits and results stay deterministic. It runs standalone on Windows or Linux, or the game's Host button starts it as a separate program.
3. **Protocol.** Today's WebSocket protocol first, so the browser client works against the Rust server during the switch. Later:
   - your own units arrive as orders plus occasional corrections;
   - enemy units arrive as positions, only while seen;
   - binary and versioned;
   - UDP through relays for public release.
4. **Unreal 5.8 client.** Drawing, HUD, effects, sound and input only. It links the core through a C interface generated by cbindgen for the rules the browser client imports today: 56 names from `shared/sim.js` (55 still used) across 35 client files, 86 names from all of `shared/` across 40, such as `placementCheck`, `canBuild`, `priceOf`, `popCap`, `CELL`, `UNITS`, `CFG`. It also uses the core to move your own units between updates.

## Two repos (2026-10-11)

Axel chose a separate repo for the native rebuild. To keep the native game measured against the JavaScript game:

- ww2-rts stays the playable game, and gameplay changes keep landing there.
- `reference/ww2-rts` is a submodule pinned to a ww2-rts commit (`e4e579a` at creation). `PARITY.md` lists what that commit does and how the native game is measured against it.
- Moving the pin is its own commit, with the port of the changed rules and the affected `PARITY.md` rows updated.

## The JavaScript game is a prototype (2026-10-12)

Julio's direction: the JavaScript game was a prototype for trying the game's ideas out, and nothing in it is set in stone. The native game keeps every feature and its intent, and improves the architecture, engineering and rules wherever it can, instead of copying the JavaScript bit for bit.

- Inside the Rust core and server, improvements need only a record here. Changes players would notice also mark their `PARITY.md` row `differs` and need Axel's agreement, since issue #4 makes behavior differences a joint decision.
- Exact comparison with the JavaScript stays where it is cheap and finds port bugs: data tables, pure functions, single-component fixtures. Whole matches are compared by outcomes agreed before the run.
- Why: copying the prototype exactly would mean copying its accidents. At the pin, one unseeded random stream is shared by every room in a process, the AI's view of the battle refreshes on a beat set by measured server time, and some unit choices depend on the spatial grid's bucket order. None of these is a design choice, and each makes matches impossible to replay. `PARITY.md` lists the proposed replacements (decisions 1 to 8).

## Reference pin (2026-10-12)

`e4e579a` stays the working pin for step 1 (#2, #3) and for `PARITY.md`. Julio and Axel choose the porting pin together at the #1 decision (Julio's ack `julio-coordination-001` on #5). The only later ww2-rts commit on 2026-10-12, `d71532c` (#66), speeds up the browser client's drawing, adds an opt-in WebTransport motion lane and fixes save loading; its `shared/` edits give the same results by inspection.

## Thousands of units

A unit is a squad or a vehicle; an infantry squad draws 15 soldiers. Four pieces are needed, and a line-by-line port won't provide them:

1. **A tick that uses every core:** vision, movement, combat and snapshots split across cores, then merge in a fixed order.
2. **Group pathfinding:** a group heading to one place shares one flow field (a map of directions toward the goal), so cost follows destinations, not units.
3. **Orders instead of positions** for your own units, which keeps the host's upload small.
4. **Cheaper crowds:** animation baked into textures and less detail with distance. This needs measuring, because the ww2-rts#64 browser experiment that moved animation work to the GPU came out slower.

## Cheating

The server is the referee and each player receives only what their own units can see.

- **Blocked by design:**
  - map hacks: hidden units, terrain and enemy plans are never sent;
  - speed, teleport, resource and health edits: those values live only on the server;
  - illegal orders: refused whole;
  - reading enemy routes and targets: they go to their owner only.
- **Needs more:**
  - host cheating: host matches that matter on a dedicated or official server;
  - FPS aimbots: Easy Anti-Cheat at public release;
  - scripts and macros: rate limits only.

## Public release

One server program covers three ways to host:

- a friend hosting from the game, through Steam or Epic relays;
- community servers on Linux;
- official servers as containers on a game hosting service.

At release the game needs:

- Steam or Epic Online Services login;
- UDP through Steam Datagram Relay or EOS relays, which hide IP addresses;
- lobbies and matchmaking;
- Easy Anti-Cheat (free with EOS on Windows, Mac, Linux and Steam Deck);
- replays (seed plus orders) for cheat reports.

Decided now so release stays cheap:

- the connection sits behind one interface;
- a player is an id from a login provider, not a room token;
- every connection starts with a protocol version check;
- the server builds as a plain Linux program that fits in a container, so it can change hosts (Hathora, a game host, shut down in May 2026).

## Rejected (2026-10-11)

- **Lockstep:** every PC would hold the full state (map hacks), the FPS view would lag by the input delay, and Mac and Windows would need bit-identical math.
- **Unreal actors and replication for gameplay:** ties rules to the engine, tests need the editor, and a dedicated Unreal server needs a source-built engine.
- **Bevy client:** weakest where this game is heavy (UI, audio, effects), with breaking releases every four to five months.
- **C++ core:** links into Unreal with no bridge, but data races and memory bugs show up only at runtime. Rust rejects most at compile time, which matters for a multithreaded tick written mostly by agents.
- **Unity:** its Terms of Service (17.2(ff)) bar AI agents and MCP clients except through Unity's own authorized framework.

## Costs

- No playing from a link: Unreal dropped HTML5 export after 4.24.
- Windows builds are made on a Windows PC.
- Unreal 5.8 is the last planned Unreal 5 release; a move to Unreal 6 comes later.
- Two build tools (cargo and Unreal's).
- Determinism needs care: Rust's default hash maps iterate in random order, and neither Rust's platform math nor the `libm` crate gives V8's results (Measurements), so the core carries its own math module.

## Deterministic match inputs (2026-10-13)

The core now has versioned random-stream state and a bounded order queue for the future match loop. The seed is recorded once. Terrain, weather, combat, off-map support and each AI seat derive a separate stream from that seed and a stable purpose key. Additional draws by one AI cannot consume another purpose's draws. Version 1 uses the wrapping integer operations in [Sebastiano Vigna's SplitMix64 reference](https://prng.di.unimi.it/splitmix64.c). It generates a 53-bit fraction for game probabilities and uses rejection sampling for bounded integers. This is simulation randomness, not a source for authentication tokens. Unknown snapshot versions and duplicate or unordered stream entries are rejected.

The queue consumes exactly one numbered tick at a time, including empty ticks. Callers assign an authoritative tick, issuer and sequence; accepted orders for that tick apply in issuer/sequence order, independent of their network arrival order. Admission policy is the caller's responsibility; a full queue rejects the next offered order. Capacity is caller-selected, and a rejected duplicate, past-tick or over-capacity order does not alter queued state. Snapshot data preserves the next tick and ordered pending commands. This replaces incidental arrival ordering inside the core; network admission and the complete command schema remain separate work. Neither component exposes a new C or WebSocket interface, and neither is a complete game loop.

Focused tests compare SplitMix64 with values from the compiled C reference, isolate purpose streams, resume streams and queues, permute arrival order, and reject invalid state. Integration with the full match simulation remains pending.

## Rust lobby and session server (2026-10-12)

`rust/crates/server` now provides `ww2-server`, a standalone HTTP/WebSocket process. Its first slice owns rooms, human and AI seats, observers, lobby settings, token reconnect/takeover, latency ping, a public room directory and cleanup. It does not start or simulate matches. Unsupported match commands return explicit denials, so clients cannot mistake a lobby for a running game.

Axum and Tokio handle transport; pure lobby transitions take an explicit monotonic time and return recipient-specific messages. Each connection has a generation identity. A replaced socket can neither mutate the room nor disconnect its replacement. Tokens stay private and retain their UTF-16 code units during truncation, so two distinct tokens cannot collide through lossy Unicode conversion. Name display at a split surrogate remains a documented difference in the server README.

Host authority follows the reference, including a spectator hosting an all-AI lobby. Directory entries require a listed room and a connected human seat. Disconnected seats remain for ten seconds; empty rooms expire after sixty. Each client has a 64-message output queue, with a slow client closed using 1013. Incoming messages are capped at 16 KiB; the current transport sends uncompressed JSON.

The server accepts missing or zero `hello.proto` and refuses unsupported versions. It sends `lobby.proto: 0`; no rules hash is advertised before a rules core is linked. The pending in-match privacy proposals are unchanged. Binding keeps the reference `HOST`/`PORT` default of `127.0.0.1:3000`, with `WW2_BIND` and then `--bind` as explicit overrides.

The live harness compares 38 lobby/directory checkpoints against the real Node server and checks all 33 map-catalog entries. It also checks version refusal, malformed input recovery, explicit start denial and oversized-message closure. Nine Rust tests cover settings, authority, identity, cleanup, limits and configuration. This is lobby compatibility for the tested cases, not full protocol or multiplayer-match completion.

The server also embeds the client-safe projection of all 33 authored maps. The generator calls the pinned reference's `mapForClient` and refuses a changed source tree. The binary serves those JSON bytes without Node or a reference checkout; it contains no raw authoring map route. Mines and their hidden material rows, triggers and scenario scripts are excluded. These projections cannot initialize an authoritative match. All editor-header map reads return 403, and map writes return 405 until the editor and full-world loader are built. A second live harness matches 96 HTTP responses against Node, including both URL forms, invalid paths, methods and credential refusal; two focused Rust tests check the embedded data and routing. Static browser hosting, map editing, authoritative world loading, compression, operatives, game simulation, snapshots and persistence remain missing.

Access needs no files, network or engine. Explicit number tags preserve Infinity, NaN and negative zero. `harness/rules-fixture.mjs` verifies the reference commit and tracked source before generating the catalog, and a fingerprint checks every compiled field.

Typed inputs admit the game's four factions and valid technology levels; unknown units/supports or impossible research states return errors. Ability overrides retain the reference's numeric values, including non-finite ones. Technology multipliers use the core's deterministic `pow`, consistent with the existing math decision.

The recorded expectations call the JavaScript helpers themselves. Tests cover 10 mode inputs, every unit/faction, 80 support cases, 640 ability cases, 480 research cases and 56,400 damage multipliers. The existing movement/vision `Rules` loader still accepts harness data. This catalog does not change the C interface or its formation-only `RULES_HASH`. At this stage, purchase execution, income, full army population counting, availability and placement were separate work; these helpers alone do not validate an order. The wallet foundation below adds income and population operations without validating purchases.

## Wallet, population and income state (2026-10-12)

`economy_state.rs` owns each player's wallet, income readouts and VP. It borrows an ordered view of units, building queues, pending drops, capture points, depots and World regions. The player vector index is the slot. This keeps the operations independent of the legacy `Game` and lets a future match runner supply authoritative state directly. World node-to-region resolution belongs to that runner; this module requires explicit regions and does not infer territory from hidden global state. The catalog now contains 47 tables, including the original exported `WORLD_TUNING`.

Population includes owned field units even when their hp is zero but they remain in the unit collection, queues only on structures, and incoming support units until their drop becomes live. Caps use the selected army size. World caps subtract all team seats from owned regions, split growth among seats not marked out, clamp before army scaling, then round. An away seat still participates in that split. A recipient-only World cap is returned unchanged.

The income phase preserves the reference's order: the leading VP total is captured before the player loop, each default-mode player's VP changes during the loop, and catch-up reads the updated team total. `Mode::Default` represents the absent mode object used by normal Conquest. Explicit Conquest, Tutorial and unknown mode objects retain the Assault fallback. Classic and World use living-unit upkeep and finished, living, owned depots; World additionally requires the depot's region to belong to its owner's team and splits regional income among teammates not marked out, including away teammates. Away or out players receive no income. Starting balances, wave and kill rewards, capture, elimination and production are outside this phase.

Three focused tests compare 37 original-JavaScript traces comprising 217 income steps and 865 player states, including all four army sizes, the seven game modes, absent and unknown modes, cutoff points, mixed teams, queues, drops, depot changes and World territory changes. Three additional World cap cases cover the clamp, eliminated teammates and fewer owned regions than seats; recipient previews and invalid-context errors are checked too. An independent review found that grouping a city's base and bonus changed the last bit: with two ordinary regions followed by a city, the source returns `5.550000000000001` MP/s. The regression now records that original-source result, and the implementation adds each base and bonus separately in source order.

Invalid slots or region indices, duplicate unit IDs, unknown catalog names, non-finite input and negative dt return errors before a wallet changes. This is a deliberate typed-input boundary in place of unchecked JavaScript objects. The fixture calls the unchanged source income block and `worldIncome` at `e4e579a`; it is component evidence, not a running match or end-to-end mode proof. Full economy and mode rows stay in progress. The server, wire snapshots, ABI and formation-only rules hash are unchanged.

## Authoritative ordinary-map loading (2026-10-12)

`map::AuthoritativeMap::from_json` accepts original authoritative JSON bytes supplied by its caller. The core performs no file, network or engine I/O. It validates ordinary legacy maps and version-2 layers, retains the complete original JSON, and exposes typed spawns, capture points, buildings, legacy triggers and normalized layers. This is separate from the server's public map projections. Those projections have already lost hidden mines, materials and scripts; the format has no provenance marker, so the caller must guarantee that the input is the original authoritative document.

`initialize_terrain` uses `Rules::compiled` and the compiled catalog to build physical flags, optional height levels, house kinds, cell HP, stone-bridge toughness, deterministic starting wear, trench directions and naval shoals. Mines remain a separate layer, so their presence does not replace the underlying physical flags. Material maps use ordered keys. `TerrainState::query_game` supplies the existing movement, vision and navigation query state, with players, units and structural sections empty. It does not create a playable match or initialize structural graphs, scenario execution, mode state or match randomness.

The bounded validator returns `Unsupported` whenever a `world`, `scenario` or `structures` property is present, including empty values. Legacy timed triggers are retained and checked against their migrated scenario bounds, but no trigger executes. Invalid supported fields return field-specific errors, without promising the JavaScript's exact error strings. JSON input is capped at 16 MiB before parsing; this is a core resource bound, separate from the reference editor's 8 MB HTTP limit. No server endpoint or C interface changes in this slice.

The recorder checks reference `e4e579a838aabae3b1d9dadbc17a0a87147bc52d` and a clean tracked source tree. It executes the original `createGame` initialization statements up to height initialization, then returns before structural setup, starting units and mode changes. All 33 authored maps and 15 valid boundary maps match the original source document, normalized layers and materials, flags, heights, house kinds, HP and wear float bits, trench-direction float bits and shoal masks. Another 55 cases record validation rejection, and three record the unsupported property boundary. The fixture includes the 1024 by 1024 size limit and Unicode string-length cases.

Issue #35 tracks this slice. The local workspace tests, strict Clippy, formatting and fixture regeneration checks pass on macOS. This is component evidence, not full `validateMap` parity, spawn-to-point reachability, mode behavior, match startup, structural destruction or Unreal integration. The affected map rows remain in progress until their complete behavior and integration checks pass. No performance measurement is claimed.

## Terrain navigation regions (2026-10-12)

`navigation.rs` ports `shared/navigation.js`: chunk-local connected regions, directed portals, region routes and limited next-leg selection. It is the coarse prerequisite for fine A*, not a complete unit pathfinder. A `TerrainView` supplies only borrowed flags, heights and version/change information; the planner cannot consult hidden terrain through another game object.

Region edges and incoming IDs keep the reference insertion order. Dirty chunks reuse freed region IDs in the same order, and route ties use region IDs. This matters because route choices can depend on update history. Direct changes or up to 32 retained changes update the affected chunks; missing continuity or a new terrain identity causes a rebuild. The route cache keeps the reference's 128-entry bound.

`NavigationLeg` borrows the cache's labels while owning its allowed-region list. Rust therefore prevents the caller from updating that cache while the fine search uses its filter. This replaces the reference's instruction to use a filter immediately with a lifetime rule.

All 4,888 recorded queries match the reference's target, connectivity, limit flag, ordered region IDs and per-cell filter. The 35 scenarios include 277 terrain updates, 1,372 limited legs and 1,268 disconnected outcomes. The recorder rejects a wrong pin or dirty tracked source. No performance claim is made. Unit path queues and integration into movement remain pending.

## Infantry and naval pathfinding (2026-10-12)

The initial `pathfinding.rs` slice added fine grid A* and path smoothing over the coarse navigation planner. `PathTerrain` supplies the terrain view plus wall proximity, known mines, fires and live bunker positions; `PathRules` supplies wall and bunker costs. The search reads no `Game` and cannot substitute hidden world state for the supplied view. That slice supported infantry and shallow/deep naval profiles; ground vehicles, aircraft, rail units and structures returned `UnsupportedProfile`.

The implementation preserves the reference's float32 path scores, score-only heap ties, neighbor order, diagonal corner checks, hazard costs, blocked-start escape and smoothing. An exhausted expansion budget has a distinct result from an unreachable route. Rust owns reusable search storage beside the navigation cache. The old undirected `regionsFor` rejection is unnecessary after the stronger directed coarse route has succeeded, so the fine search does not duplicate that cache.

The original `findPath` produces 1,175 oracle searches across all 33 authored maps and crafted terrain cases: 914 found routes, 163 unreachable results and 98 budget exhaustions. Every waypoint and resolved endpoint matches bit for bit, as do expansion counts and outcomes. Repeated searches after mine, fire and bunker changes are included. The recorder verifies the exact reference pin and rejects tracked changes. At that stage, vehicle clearance, automatic recipient-view selection, retry policy, request scheduling and movement integration remained separate work. No performance claim was made.



## Internal Rust recipient view (2026-10-12)

`rust/crates/core/src/client_view.rs` is an internal Rust decoder of the pinned reference protocol. It holds one recipient's received knowledge, resets on each start, applies held-unit deltas and fog XOR updates, and retains raw terrain rows and HUD messages. Inputs are validated before mutation, with limits of 16 MiB per message, four million map cells and 100,000 held units. Pending terrain-cell changes accumulate until drained. The transport owns resync requests and their rate limit.

The view exposes typed unit rows and retains complete raw rows and extra fields. Its terrain cache is the latest received row per cell, not composed terrain or placement-query parity. Raw seen and explored masks exclude rendering effects such as fading, temporary unit illumination and lifting fog after a match. Unknown message types leave the view unchanged.

`harness/protocol-record.mjs` captures complete, sanitized reference messages. `harness/view-check.mjs` reads back the pinned browser's unit state and fog masks and exercises its cell-application functions with rendering dependencies stubbed. All 1,236 expected reports cover two recipients in Conquest and World Conquest. `simtest --view` compares these received-state reports, including raw terrain-row caches. Gzip belongs to simtest, not the core. Reconnects, operative sessions, save/load and transport behavior remain outside these recordings.

This extraction adds no C functions or consumer contract. ABI 1, the generated header and the formation-only rules hash remain unchanged. PR #16 retains the six proposed C view calls and ABI 2 transition pending Axel's explicit approval. Pure Rust callers can use the internal view independently of that review; Unreal integration and the remaining terrain and availability queries are separate work.

## Pure projectile flight and contact helpers (2026-10-12)

`rust/crates/core/src/projectiles.rs` provides typed, standalone versions of all pure helpers in the pinned `shared/projectiles.js`: profile selection, flight position and velocity, launch solutions, box/body/naval-hull sweeps, segment distance, crossed-cell traversal and material ricochet response. The module has no game-state, renderer or networking dependency. Projectile and material constants stay beside these helpers for now; they are not part of the compiled catalog or the public rules hash.

The port keeps source arithmetic, x/y/z slab order, corner-cell order, strict earliest-hit comparisons, box-before-cap ties and bounded rotational pieces. Trigonometry and two/three-argument hypot use the core's own math; square roots use the same hardware operation as the math module. The checked API rejects nonfinite inputs, reversed bounds, negative radii/lengths and nonpositive explicit flight durations. Grid dimensions are limited to 2^26 cells per side with an area fitting `usize`; hull angle wrapping allows at most 4,096 full-turn reductions. These limits prevent malformed input from overflowing indexing or keeping a tick in an unbounded loop.

`harness/projectile-fixture.mjs` calls the original helpers with x64 Node 24.21.0, refuses a changed reference pin or tracked source tree, and records exact floating-point bits. Six focused tests pass in debug and release on the Mac, covering 941 oracle cases: all profile/material constants, precedence, zero/negative elapsed time, launch arcs, tangent and corner contacts, translating bodies, rotating naval hulls, grid-cell order and ricochet thresholds. Strict core Clippy and formatting checks pass. This is pure-helper evidence only. Combat firing, flight expiry, game-world contact selection, damage, terrain changes and random scatter are not connected yet; CMB-48, CMB-49, CMB-50 and CMB-160 remain in progress.

## Ground-vehicle pathfinding (2026-10-12)

Issue #34 extends the initial infantry/naval search to all 12 non-rail ground types, including the lorry and Kaiju fallback profiles. A private vehicle navigation cache expands blocked cells by the hull's turning radius and rejects destinations without that clearance. `PathTerrain` adds explicit observed wear, public wetness and road presence; `PathRules` adds ground-speed constants. Road, mud, wood, ford and churn costs refresh for each search, as do mines, fires and bunkers. Road-aware estimates and smoothing preserve the chosen road route. The caller still supplies the entire terrain view; no `Game`, hidden world or automatic knowledge selection is consulted.

The footprint cache uses the block mask and radius, source storage and recipient identity, and explicit terrain versions. Direct changes or a complete history expand only the affected cells. Missing history or changed source identity rebuilds the footprint. Expanded cells retain first-encounter order from the supplied changes and each row-major neighborhood, because the coarse planner's region reuse and tied routes can depend on that order. A private update counter also invalidates the coarse cache when a source array is replaced at unchanged versions, even if the footprint allocation is reused. Storage addresses serve only as cache identity, never as an ordering key.

The extended original-JavaScript fixture has 1,529 searches: 1,108 found routes, 299 unreachable results and 122 expansion limits. All 1,175 earlier infantry/naval query records are unchanged; 354 vehicle cases add road and terrain costs, bridge and narrow-gap clearance, elevation, blocked goals, dynamic terrain, source replacement and reverse-order distant edits. Waypoints and resolved destinations match bit for bit, with identical expansion counts and outcomes. Cache regression checks also cover unchanged reuse, direct and historical changes, a missing-history rebuild and recipient identity changes. The recorder checks the exact reference pin and rejects tracked source changes. Core/simtest tests, strict Clippy, formatting and fixture regeneration pass on macOS; cross-platform CI remains the delivery gate.

Aircraft, trains and structures still return `UnsupportedProfile`. Automatic recipient-view selection, retry policy, request scheduling and movement integration remain separate work. MOV-27 and MOV-28 are in progress, since search fixtures alone do not verify vehicle driving or an end-to-end match. No ABI or wire interface changed, and no performance claim is made.


## Routing inside movement (2026-10-13)

The movement block now has `move_unit_with_routes` and `move_units_with_routes` entry points. They invoke the caller's route handler at the reference's actual recovery point, after traffic has selected its steering goal. Infantry stalls request budgeted recovery; vehicle stalls and traffic replans request an immediate search. The handler owns terrain selection, scheduling, errors and path replacement. A replaced path advances `path_gen`, preserving the identity checks used by lane and clearance caches. Existing entry points retain the disabled-search behavior needed by the frozen benchmark.

Four original-JavaScript recordings run real fine searches inside movement for infantry and tanks on passable and disconnected maps. Across 48 ticks, all movement fields, separation and infantry progress match. The recorder restores the three disabled search hooks in the existing workload and supplies an explicit observed terrain view; other workload exclusions remain. This verifies the fine-search-to-movement connection, not a full match loop, recipient knowledge selection, logistics or combat. The standalone scheduler is a separate integration step.

## The core's math (2026-10-12)

The core carries its own math (`rust/crates/core/src/math.rs`) instead of Rust's `f64` methods, which call each platform's C library. It ports V8's fdlibm (`src/base/ieee754.cc` as Node 24.21.0 compiles it) and V8's `Math.hypot`, plus JavaScript's `round`, `max`, `min` and `sign`, so every platform computes the same bits and they equal the JavaScript game's.

- **The reference runtime is x64 Node.** Clang builds V8's fdlibm for arm64 with `a * b + c` fused into one rounding, so Node on Apple Silicon gives different last bits from x64 Node for every fdlibm function (Measurements). Baseline x86-64 has no fused instruction, so x64 Node computes the C source as written on every operating system, and the core follows the source. Parity runs and fixtures use x64 Node 24.21.0: the Vostro, or the darwin-x64 build under Rosetta on the Mac. `harness/math-fixture.mjs` refuses to run on arm64.
- **`pow` uses V8's own fdlibm `pow`,** after JavaScript's special cases (exponent 2 is `x * x`, exponent 0.5 is a square root). Node's default `pow` calls the operating system's, so the JavaScript game can differ between operating systems; the core gives one answer everywhere. It differs from default Node on about 6 to 10% of inputs, in the last bit. A deliberate difference (`docs/parity/interface.md`, IF-17).
- **The JavaScript game is not reproducible across CPU types either:** a seeded match on Apple Silicon and the same match on an x64 machine can diverge at the first last-bit difference. Reference runs that must agree are made on x64.

## Vision and fog in the core (2026-10-12)

`updateVision` and `teamFog` are ported to `rust/crates/core/src/vision.rs` and `fog.rs` and give the reference's answers exactly (Measurements). The data they read is in `game.rs` (the state) and `rules.rs` (unit kinds and the vision numbers, loaded from the reference's own tables until the core owns them, IF-01).

- **The fog caches sit beside the game, not in it.** The JavaScript keeps the fog terrain tables, the kept cells of still sources and each team's fog on the game object. Here they are one `Fog` value next to the `Game`, so the fog pass reads the game and writes only its own caches. That lets each team's fog run on its own thread (`Fog::teams_threaded`): a unit's kept cells belong to its own team's pass, so the teams write nothing in common, and the results merge back in team order. The answers equal one team after another.
- **Smoke keeps its identity.** A kept source remembers the smoke clouds near it by object identity in the JavaScript, so a cloud that drifts does not make it look again. Each `Smoke` carries an id that stands for that identity. The harness codec does not keep identity, so a source loaded from a state file remembers clouds that match none of the game's, as in the reference after decoding.
- **Units are in ascending id order.** The reference iterates its units Map in insertion order; ids only grow and no unit is put back, so `Game::units` is a `BTreeMap` by id. The loader refuses a state where the Map is in another order.
- **Ported as the reference has it, for now:** the fog's sight walk ignores the woods depth rule that `los` applies (`docs/parity/combat.md`, limitations), and the vision pass still runs one team after another.
- **Not ported yet** (Conquest does not use them): Horde stragglers and the Kaiju shown through the fog, the remembered enemy buildings of Classic and World Conquest, World Conquest's guards and its visible-cell list.

## Formation spots and the first C calls (2026-10-12)

`shared/formation.js` is ported to `rust/crates/core/src/formation.rs` and gives the reference's spots bit for bit; `rust/crates/ffi` (`ww2-ffi`) exposes it to Unreal (`docs/contracts/rust-unreal-abi.md`, First calls).

- **Sorts follow V8 exactly.** `sort.rs` ports the whole TimSort that Node 24.21.0 runs for `Array.prototype.sort` (`third_party/v8/builtins/array-sort.tq`): runs, binary insertion, the run stack, merges and galloping. Every stable sort agrees when the comparator is consistent, but `facingSpots` rounds how far forward a unit stands to the centimetre, and `Math.round(0.5)` is 1 while `Math.round(-0.5)` is -0. Units a few millimetres apart then compare as tied one way round and not the other, and the order depends on which pairs the sort compares. With a plain stable insertion sort in its place, 2,000 of the fixture's 10,300 seeded cases came out different. The fixture reaches every branch of the merge code except `MergeForceCollapse` picking the lower pair, which the run stack's invariants seem to rule out. Other sorts in the port (IF-25) can use the same function.
- **The C interface takes no shortcuts with C values.** Booleans cross as `uint8_t`, so no byte from C is an invalid Rust `bool`; shapes cross as `int32_t` constants, and an unknown one is an error rather than a Rust enum with an invalid value. A null pointer with a zero length is accepted, because an empty Unreal `TArray` hands over a null pointer.
- **`ww2_formation_spots` reports a count.** The draft had none, but the JavaScript returns no spots at all for a line or block whose average slot times spread is NaN, or 0 with no drag, so the call writes `*out_len`.
- **The last error stays until the next failure,** like `errno`: a successful call does not clear it, and reading it does not change it.
- **The header is checked by a test, not written by the build.** cbindgen is a dev-dependency, so building the static library needs only the core. `tests/header.rs` compares the committed header with cbindgen's output and fails when they differ.

## Movement and crowd separation in the core (2026-10-12)

The movement block of `step()`'s unit loop and `separateCrowds` are ported to `rust/crates/core/src/movement.rs`, `traffic.rs`, `vehicle.rs`, `terrain.rs` and `separation.rs`, and give the reference's answers call by call (Measurements).

- **What the block is.** From the traffic step ("Global waypoints, voluntary traffic steering and swept contact are separate steps") through `updateGrid` and what follows it in the frozen workload: the dust flag, `still`, the end of a finished retreat and the vehicles' stuck count. The infantry stuck count runs after separation (`infantry_progress`), as in the reference. `move_units` also has the parts of the loop around the block that movement reads: which units reach it, the suppression speed factor taken at the start of a unit's turn, and the suppression, route and sprint timers running down.
- **Left out for now,** so a game that uses them differs from the reference there: path searches (a unit that stalls, or that traffic tells to find a new route, keeps its route and asks again in a second, which is what the frozen workload's patch does); logistics (fuel limits and fuel use, convoys, units forced back by shortages; the loader refuses units with reserves, a convoy or an operative rather than move them wrongly); crushing, ground wear and mud it makes, and mines going off under a unit; World Conquest's road march; riders placed on their carrier; trains and planes; and each player's remembered view of the map (traffic steers by the real map, as in the workload). With wear unchanged, `touch` only tells clients about a cell whose look changed; the trace checks none did.
- **Route identity.** The reference compares routes by array identity: a lane scan or a vehicle's clearance is redone when `u.path` is a new array. Each unit carries `path_gen`, raised whenever it gets a new route array, and `LaneScan` and `Clearance` keep the value they were made with. The harness's state files lose identity, so a loaded unit's scan and clearance count as made on another route, as in the reference after decoding.
- **A missing field reads as the reference reads it.** A field read with `??` gets that fallback when loaded (`trafficWait`, `ghost`, `moveSpeed`...), a number read without one is NaN (which compares and adds as `undefined` does: `stuck`, `repath`, `pace`), a field read only for its truth is a `bool` (`drift`, `holdPos`, `build`), and a field read with `??` but whose absence matters later stays an `Option` (`vx`, `travelDir`, `dust`).
- **The moving unit is out of the unit map while its block runs.** The reference reads the moving unit through the map only in `waitsOn`, which stops at it either way because its `queuedBehind` is 0 by then, and every query skips it; taking it out lets the block borrow it mutably while reading the others.
- **Movement and separation stay on one thread.** Each unit's step reads where the units before it ended up, and unordered spatial queries return bucket order, which the earlier units' moves change. The vision pass now also has a threaded form (`update_vision_threaded`): a team's view only reads the game, so the teams run one per thread and the results are handed out in player order, equal to one team after another.
- **Found in the reference:** `shared/sim.js` defines its own `ghostPair(g, a, b)` (allied, and either a ghost) over the one it imports from `local-traffic.js`, so separation's solid contact is softened for ghosts; the imported three-argument form would never be. `suppMul` is taken before suppression wears off in the same tick. `weather()` dries and soaks the ground every tick even in the frozen workload; the trace records the wetness per tick, and the Rust workload leaves the living ground out.
