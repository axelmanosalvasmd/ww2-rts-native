## Why native (2026-10-11)

Measured in ww2-rts:

- **Server:** one battle's tick runs on one thread. A heavy Conquest battle (Six Fronts, six Massive AI, about 400 units) costs 16.3 ms mean and 34.0 ms p95 of the 50 ms tick in Node (`tools/bench.mjs`, ww2-rts#58). Bun is 1 to 14% faster. `WW2_SHARDS=N` (`server/shards.js`) spreads separate rooms over processes, but nothing splits one battle.
- **Client:** the browser's main thread draws, builds terrain and runs game logic. A three-human Huge World Conquest session fell to 0.7 FPS; after the ww2-rts#61 fixes it runs at about 30 FPS on an RTX 4060 with 12.6 ms of frame-loop JavaScript.
- **Crowds:** 2,160 soldiers near the camera run at about 35 FPS on Low and 21 to 23 on High in the ww2-rts#64 synthetic fixture; the GPU spends 22 to 41 ms a frame on that scene.

The goal is thousands of units per battle and a public release later. ww2-rts#64 concluded its own measurements don't justify a rewrite, so step 1 measures before anything is ported.

Two programs talking over the network, as today. Only the rules core decides outcomes.

1. **Rules core (Rust, `rust/crates/core`).** Port of `shared/`. 20 ticks a second. The same seed gives the same match. Unit, weapon and map tables live in data files both sides read. No engine, networking or file-system code.
2. **Room host (`ww2-server`, Rust).** One thread per room; a battle's tick is split across cores and merged in a fixed order. AI planning and long path searches run on worker threads and apply at a fixed future tick, so the battle never waits and results stay deterministic. It runs standalone on Windows or Linux, or the game's Host button starts it as a separate program.
3. **Protocol.** Today's WebSocket protocol first, so the browser client works against the Rust server during the switch. Later:
   - your own units arrive as orders plus occasional corrections;
   - enemy units arrive as positions, only while seen;
   - binary and versioned;
   - UDP through relays for public release.
4. **Unreal 5.8 client.** Drawing, HUD, effects, sound and input only. It links the core through a C interface generated by cbindgen for the rules the browser client imports today: 56 names from `shared/sim.js` (55 still used) across 35 client files, 86 names from all of `shared/` across 40, such as `placementCheck`, `canBuild`, `priceOf`, `popCap`, `CELL`, `UNITS`, `CFG`. It also uses the core to move your own units between updates.

## The JavaScript game is a prototype (2026-10-12)

Julio's direction: the JavaScript game was a prototype for trying the game's ideas out, and nothing in it is set in stone. The native game keeps every feature and its intent, and improves the architecture, engineering and rules wherever it can, instead of copying the JavaScript bit for bit.

- Inside the Rust core and server, improvements need only a record here. Changes players would notice also mark their `PARITY.md` row `differs` and need Axel's agreement, since issue #4 makes behavior differences a joint decision.
- Exact comparison with the JavaScript stays where it is cheap and finds port bugs: data tables, pure functions, single-component fixtures. Whole matches are compared by outcomes agreed before the run.
- Why: copying the prototype exactly would mean copying its accidents. At the pin, one unseeded random stream is shared by every room in a process, the AI's view of the battle refreshes on a beat set by measured server time, and some unit choices depend on the spatial grid's bucket order. None of these is a design choice, and each makes matches impossible to replay. `PARITY.md` lists the proposed replacements (decisions 1 to 8).

## Thousands of units

A unit is a squad or a vehicle; an infantry squad draws 15 soldiers. Four pieces are needed, and a line-by-line port won't provide them:

1. **A tick that uses every core:** vision, movement, combat and snapshots split across cores, then merge in a fixed order.
2. **Group pathfinding:** a group heading to one place shares one flow field (a map of directions toward the goal), so cost follows destinations, not units.
3. **Orders instead of positions** for your own units, which keeps the host's upload small.
4. **Cheaper crowds:** animation baked into textures and less detail with distance. This needs measuring, because the ww2-rts#64 browser experiment that moved animation work to the GPU came out slower.

## Cheating

The server is the referee and each player receives only what their own units can see.

- **Blocked by design:**
  - map hacks: hidden units, terrain and enemy plans are never sent;
  - speed, teleport, resource and health edits: those values live only on the server;
  - illegal orders: refused whole;
  - reading enemy routes and targets: they go to their owner only.
- **Needs more:**
  - host cheating: host matches that matter on a dedicated or official server;
  - FPS aimbots: Easy Anti-Cheat at public release;
  - scripts and macros: rate limits only.

## Public release

One server program covers three ways to host:

- a friend hosting from the game, through Steam or Epic relays;
- community servers on Linux;
- official servers as containers on a game hosting service.

At release the game needs:

- Steam or Epic Online Services login;
- UDP through Steam Datagram Relay or EOS relays, which hide IP addresses;
- lobbies and matchmaking;
- Easy Anti-Cheat (free with EOS on Windows, Mac, Linux and Steam Deck);
- replays (seed plus orders) for cheat reports.

Decided now so release stays cheap:

- the connection sits behind one interface;
- a player is an id from a login provider, not a room token;
- every connection starts with a protocol version check;
- the server builds as a plain Linux program that fits in a container, so it can change hosts (Hathora, a game host, shut down in May 2026).

## Rejected (2026-10-11)

- **Lockstep:** every PC would hold the full state (map hacks), the FPS view would lag by the input delay, and Mac and Windows would need bit-identical math.
- **Unreal actors and replication for gameplay:** ties rules to the engine, tests need the editor, and a dedicated Unreal server needs a source-built engine.
- **Bevy client:** weakest where this game is heavy (UI, audio, effects), with breaking releases every four to five months.
- **C++ core:** links into Unreal with no bridge, but data races and memory bugs show up only at runtime. Rust rejects most at compile time, which matters for a multithreaded tick written mostly by agents.
- **Unity:** its Terms of Service (17.2(ff)) bar AI agents and MCP clients except through Unity's own authorized framework.

## Recipient terrain for routing (2026-10-12)

`route_knowledge.rs` composes a routing and cover view from explicit public authored terrain or ordered remembered cell rows. Observed mode starts from the supplied authored terrain, removes initial hidden mine markers and retains supplied shoals. World mode starts with unknown cells: open flags, zero height and wear, and no remembered mine or cover metadata. Applying rows never reads a `Game`, collects visibility or substitutes authoritative terrain. Live fires, bunker positions, roads and wetness enter through `LiveRouting`; cover queries take already filtered wrecks. Their producers remain responsible for visibility and public-data policy.

Each row carries a caller-supplied revision scoped to its cell. The same revision skips the row before interpreting its contents, matching the reference's row-object identity check. A fresh equal-content row still advances the Observed version. World advances routing versions only for changed flags or height, or its initial team-view binding; a repeated World memory version skips the whole pass. Both modes preserve input change order and a 32-record navigation history. Metadata retains material overrides when omitted, clears omitted sections and trench fronts, and stores remembered HP, wear and fronts at the reference's float32 precision.

`CoverBasis` records public or remembered house kind and toughness when the character and section data do not determine full HP. An active section's supplied maximum needs no fallback. Unknown World cells return `UnknownCell` for cover queries; an incomplete known-cell basis returns `MissingCoverBasis`. Routes can still use that cell's known flags. This is an explicit integration boundary: the reference inherits `house` and `tough` from its full game object, but a native producer must establish which of those values are public or remembered before supplying them. The module does not infer hidden house extents or silently assume toughness one for World cover.

The recorder loads the pinned original helpers in memory with additional exports and supplies their memory rows directly. It changes no reference files and rejects a wrong pin or tracked source edits. The oracle checks 93 snapshots, 270 infantry/vehicle/naval routes and 48 cover query sets across crafted Observed/World sequences and three authored maps. It covers row identity, layer composition, mine ownership and remembered removal, float32 cover metadata, material precedence, settled and moving wrecks, fires, wall updates, trim fallback, history rollover and changes to unused authoritative arrays. Separate tests check missing cover inputs and atomic rejection of invalid row batches.

The observed producer below now forwards full remembered rows in first-insertion order and retains stable revisions. World memory still needs a producer that preserves the resolved journal order. The current `ClientView` cell map and sorted change list are insufficient to recover that order. Receive order alone is not a general replacement: the reference's snapshot outbox can reorder repeated edits while its remembered map retains first-insertion order. If a wire adapter cannot reconstruct that order, its producer must retain or supply it explicitly. This remains a producer-contract decision; the module does not invent ordering metadata or change the wire format. This slice does not change that decoder or the ABI, build a World memory collector, select a recipient automatically, perform the bank step-back fallback, schedule searches or integrate them with movement. MOV-29 remains in progress. No performance claim is made.


## Internal observed terrain memory (2026-10-12)

`observed_memory.rs` collects an ordinary map's per-player memory from `World` cell logs and caller-supplied visibility facts. It replays pending log indices in ascending order, reading current cell data and filtering hidden mine metadata before comparison or storage. Equal rows retain their revision and acknowledge the pending entry before visibility checks, as the source does. Hidden mines can reveal a changed physical surface while staying pending; an unchanged physical character, height and packed state suppresses a hidden mine's metadata-only update. A new terrain/vision key permits replay. Reveal and skip-fog bypass ordinary cell visibility, but do not bypass footprint visibility or hidden-mine suppression.

`ObservationFacts` supplies cell visibility, mine knowledge/ownership and building footprint facts. `FootprintFact.identity` identifies the same live or ruined footprint object across its cells; its visibility result is cached for that refresh. Allied footprints are visible. Live footprints use the player's visible-unit membership; ruins use the caller's team visibility at the footprint's position. The caller must supply the original player/team eligibility semantics and keep one producer with that player. This module does not calculate fog, select an owner automatically or read unavailable combat fields.

Full rows retain first-insertion order when replaced. A separate outbox removes and reinserts a changed cell so snapshots receive the latest-edit order; draining it never consumes full route or reconnect reads. Accepted replacements alone advance a checked revision counter. Updates and acknowledgments are staged before mutation, so invalid rows or revision exhaustion leave memory, outbox, replay key and World pending sets unchanged. The initial terrain allocation identifies the map binding, and a changed map requires new memory. Route forwarding rejects mismatched dimensions, recipient identity or World-mode views and passes only the full remembered order to `RouteKnowledge`. Callers retain the original route-view tick/terrain/vision cache separately from the collector's terrain/vision key.

The recorder runs the original `observedTerrainFor`, `seenWorldCell` and `observedPathView` bodies from the clean pinned reference. It stops match construction after actual map/structure setup and replaces only the visibility predicate with explicit team facts. ## The core's math (2026-10-12)

The core carries its own math (`rust/crates/core/src/math.rs`) instead of Rust's `f64` methods, which call each platform's C library. It ports V8's fdlibm (`src/base/ieee754.cc` as Node 24.21.0 compiles it) and V8's `Math.hypot`, plus JavaScript's `round`, `max`, `min` and `sign`, so every platform computes the same bits and they equal the JavaScript game's.

- **The reference runtime is x64 Node.** Clang builds V8's fdlibm for arm64 with `a * b + c` fused into one rounding, so Node on Apple Silicon gives different last bits from x64 Node for every fdlibm function (Measurements). Baseline x86-64 has no fused instruction, so x64 Node computes the C source as written on every operating system, and the core follows the source. Parity runs and fixtures use x64 Node 24.21.0: the Vostro, or the darwin-x64 build under Rosetta on the Mac. `harness/math-fixture.mjs` refuses to run on arm64.
- **`pow` uses V8's own fdlibm `pow`,** after JavaScript's special cases (exponent 2 is `x * x`, exponent 0.5 is a square root). Node's default `pow` calls the operating system's, so the JavaScript game can differ between operating systems; the core gives one answer everywhere. It differs from default Node on about 6 to 10% of inputs, in the last bit. A deliberate difference (`docs/parity/interface.md`, IF-17).
- **The JavaScript game is not reproducible across CPU types either:** a seeded match on Apple Silicon and the same match on an x64 machine can diverge at the first last-bit difference. Reference runs that must agree are made on x64.

## Vision and fog in the core (2026-10-12)

`updateVision` and `teamFog` are ported to `rust/crates/core/src/vision.rs` and `fog.rs` and give the reference's answers exactly (Measurements). The data they read is in `game.rs` (the state) and `rules.rs` (unit kinds and the vision numbers, loaded from the reference's own tables until the core owns them, IF-01).

- **The fog caches sit beside the game, not in it.** The JavaScript keeps the fog terrain tables, the kept cells of still sources and each team's fog on the game object. Here they are one `Fog` value next to the `Game`, so the fog pass reads the game and writes only its own caches. That lets each team's fog run on its own thread (`Fog::teams_threaded`): a unit's kept cells belong to its own team's pass, so the teams write nothing in common, and the results merge back in team order. The answers equal one team after another.
- **Smoke keeps its identity.** A kept source remembers the smoke clouds near it by object identity in the JavaScript, so a cloud that drifts does not make it look again. Each `Smoke` carries an id that stands for that identity. The harness codec does not keep identity, so a source loaded from a state file remembers clouds that match none of the game's, as in the reference after decoding.
- **Units are in ascending id order.** The reference iterates its units Map in insertion order; ids only grow and no unit is put back, so `Game::units` is a `BTreeMap` by id. The loader refuses a state where the Map is in another order.
- **Ported as the reference has it, for now:** the fog's sight walk ignores the woods depth rule that `los` applies (`docs/parity/combat.md`, limitations), and the vision pass still runs one team after another.
- **Not ported yet** (Conquest does not use them): Horde stragglers and the Kaiju shown through the fog, the remembered enemy buildings of Classic and World Conquest, World Conquest's guards and its visible-cell list.

## Formation spots and the first C calls (2026-10-12)

`shared/formation.js` is ported to `rust/crates/core/src/formation.rs` and gives the reference's spots bit for bit; `rust/crates/ffi` (`ww2-ffi`) exposes it to Unreal (`docs/contracts/rust-unreal-abi.md`, First calls).

- **Sorts follow V8 exactly.** `sort.rs` ports the whole TimSort that Node 24.21.0 runs for `Array.prototype.sort` (`third_party/v8/builtins/array-sort.tq`): runs, binary insertion, the run stack, merges and galloping. Every stable sort agrees when the comparator is consistent, but `facingSpots` rounds how far forward a unit stands to the centimetre, and `Math.round(0.5)` is 1 while `Math.round(-0.5)` is -0. Units a few millimetres apart then compare as tied one way round and not the other, and the order depends on which pairs the sort compares. With a plain stable insertion sort in its place, 2,000 of the fixture's 10,300 seeded cases came out different. The fixture reaches every branch of the merge code except `MergeForceCollapse` picking the lower pair, which the run stack's invariants seem to rule out. Other sorts in the port (IF-25) can use the same function.
- **The C interface takes no shortcuts with C values.** Booleans cross as `uint8_t`, so no byte from C is an invalid Rust `bool`; shapes cross as `int32_t` constants, and an unknown one is an error rather than a Rust enum with an invalid value. A null pointer with a zero length is accepted, because an empty Unreal `TArray` hands over a null pointer.
- **`ww2_formation_spots` reports a count.** The draft had none, but the JavaScript returns no spots at all for a line or block whose average slot times spread is NaN, or 0 with no drag, so the call writes `*out_len`.
- **The last error stays until the next failure,** like `errno`: a successful call does not clear it, and reading it does not change it.
- **The header is checked by a test, not written by the build.** cbindgen is a dev-dependency, so building the static library needs only the core. `tests/header.rs` compares the committed header with cbindgen's output and fails when they differ.

## Movement and crowd separation in the core (2026-10-12)

The movement block of `step()`'s unit loop and `separateCrowds` are ported to `rust/crates/core/src/movement.rs`, `traffic.rs`, `vehicle.rs`, `terrain.rs` and `separation.rs`, and give the reference's answers call by call (Measurements).

- **What the block is.** From the traffic step ("Global waypoints, voluntary traffic steering and swept contact are separate steps") through `updateGrid` and what follows it in the frozen workload: the dust flag, `still`, the end of a finished retreat and the vehicles' stuck count. The infantry stuck count runs after separation (`infantry_progress`), as in the reference. `move_units` also has the parts of the loop around the block that movement reads: which units reach it, the suppression speed factor taken at the start of a unit's turn, and the suppression, route and sprint timers running down.
- **Left out for now,** so a game that uses them differs from the reference there: path searches (a unit that stalls, or that traffic tells to find a new route, keeps its route and asks again in a second, which is what the frozen workload's patch does); logistics (fuel limits and fuel use, convoys, units forced back by shortages; the loader refuses units with reserves, a convoy or an operative rather than move them wrongly); crushing, ground wear and mud it makes, and mines going off under a unit; World Conquest's road march; riders placed on their carrier; trains and planes; and each player's remembered view of the map (traffic steers by the real map, as in the workload). With wear unchanged, `touch` only tells clients about a cell whose look changed; the trace checks none did.
- **Route identity.** The reference compares routes by array identity: a lane scan or a vehicle's clearance is redone when `u.path` is a new array. Each unit carries `path_gen`, raised whenever it gets a new route array, and `LaneScan` and `Clearance` keep the value they were made with. The harness's state files lose identity, so a loaded unit's scan and clearance count as made on another route, as in the reference after decoding.
- **A missing field reads as the reference reads it.** A field read with `??` gets that fallback when loaded (`trafficWait`, `ghost`, `moveSpeed`...), a number read without one is NaN (which compares and adds as `undefined` does: `stuck`, `repath`, `pace`), a field read only for its truth is a `bool` (`drift`, `holdPos`, `build`), and a field read with `??` but whose absence matters later stays an `Option` (`vx`, `travelDir`, `dust`).
- **The moving unit is out of the unit map while its block runs.** The reference reads the moving unit through the map only in `waitsOn`, which stops at it either way because its `queuedBehind` is 0 by then, and every query skips it; taking it out lets the block borrow it mutably while reading the others.
- **Movement and separation stay on one thread.** Each unit's step reads where the units before it ended up, and unordered spatial queries return bucket order, which the earlier units' moves change. The vision pass now also has a threaded form (`update_vision_threaded`): a team's view only reads the game, so the teams run one per thread and the results are handed out in player order, equal to one team after another.
- **Found in the reference:** `shared/sim.js` defines its own `ghostPair(g, a, b)` (allied, and either a ghost) over the one it imports from `local-traffic.js`, so separation's solid contact is softened for ghosts; the imported three-argument form would never be. `suppMul` is taken before suppression wears off in the same tick. `weather()` dries and soaks the ground every tick even in the frozen workload; the trace records the wetness per tick, and the Rust workload leaves the living ground out.

Rust's whole tick averages 17.1 ms with a p95 of 21.6, inside the 50 ms tick; Node's frozen `step()` averages 34.4 ms with a p95 of 55.0, over it.
- **Vision and fog gain most:** fog is 2.9 times faster on one thread and 7.9 times with a thread per team; vision 2.5 times, and 6.6 times threaded.
- **Movement gains 2.1 times and separation 1.4 times,** and neither uses threads, because each unit's step reads where the units before it ended up. Spatial-index lookups take about 36% of Rust's time (one `BTreeMap` lookup per candidate unit). Storing units by slot is the obvious next step, and the plan's group pathfinding and parallel tick (`DESIGN.md`, "Thousands of units") are the larger ones.
- **The parity result:** the vision and fog passes give the JavaScript's answers exactly on all four states; movement and separation match call by call over 200 ticks of each frozen state (646,400 calls, 1,360,000 unit states); the math matches x64 Node bit for bit. Whole ticks are not compared, because the port leaves out code that also moves units (`PARITY.md`, "How parity is judged").
